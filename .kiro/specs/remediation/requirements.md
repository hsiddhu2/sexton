# Requirements Document

## Introduction

The remediation module adds to the Sexton Engine (`packages/engine`) the step that turns a scored report into proposals: for each package in state Haunted, Dead or Possessed, exactly one Remediation plan, and for each plan that can be carried out a PR intent that an Executor turns into a branch, a commit and a pull request. It adds a pure planner `planRemediation`, a pure bump selector `selectBump`, a bump data fetch `gatherBumpData` that reads the full packument and OSV through the existing Transport and Cache, an empty Recipe registry, a pure branch-name function, a pure PR intent builder `buildPrIntent`, a pure PR body builder `buildPrBody`, an append-only Remediation log interface with an in-memory implementation, and `attachRemediations`, which builds the `remediations` list of the API response. It changes the API contract type `RemediationEntry` and the web validator that checks it.

This spec implements R-RM-1, R-RM-2, R-RM-3, R-RM-5, R-RM-6 and R-RM-8 of docs/requirements.md on the engine side, and R-SG-3, R-SG-7, R-SG-8 and R-SG-9 as they apply to the new reads, and N-2 in part. The split is as follows. The Engine plans and describes. Something else executes. R-RM-1: the Engine proposes one plan per unhealthy package. R-RM-2: the Engine selects the bump version; where this spec departs from the wording of R-RM-2 (candidates are only versions greater than the installed version, one budget of 20 candidates is shared by the in-range and out-of-range groups, and "lowest" means lowest in Candidate order) it says so in Requirement 2. R-RM-3: the Engine proposes remove only when the caller supplies an Import sites count of exactly 0; counting import sites is the caller's job, because the Engine never reads repository source files. R-RM-4: the Engine ships an empty Recipe registry and a migrate branch in the kind order; the node-sass to sass recipe is a later spec. R-RM-5: the Engine produces the PR intent, with a branch named `sexton/<kind>-<package>`; creating the branch, committing, opening the pull request, resolving the default branch and refusing to push to it are the Executor's job (the api or the agent, through GitHub MCP). R-RM-6: the Engine renders the PR body for bump and remove; the migration sections (files changed, sites left for human review) come with the recipe spec. R-RM-8: the Engine defines the Remediation log entry and an append-only interface; recording every PR in the log before returning (pr-safety.md) is the Executor's duty.

The spec reuses, and does not change, the Signal envelope, `scorePackages`, `evaluatePolicy`, the `Transport` and `requestWithRetry` (User-Agent, backoff on 429 and 503, R-SG-8, R-SG-9), `CachedFetcher` and `cacheKey` (R-SG-7), `ClientContext`, `readFullPackument` and the `npm-packument` cache key, `extractDeprecated`, `isValidPackageName`, `isResolvableRange`, `IntakePackage` with `declaredRange` and `origin`, `ENGINE_VERSION`, and the OSV helpers `fetchAdvisory` and `OSV_MAX_PAGES`. Every upstream request goes through the Transport and the Cache. The new Engine code lives in `packages/engine/src/remediation/`, one exported concept per file. The one addition to a client file is a batched OSV query in `packages/engine/src/clients/osv.ts`.

Six changes touch existing code and need review. First, `RemediationEntry` moves its definition to the Engine types and `packages/api/src/contract.ts` re-exports it, as it already does for `Advisory` and `PolicyResult`, because the Engine depends on nothing internal and `attachRemediations` must return the type (Requirement 7). The old placeholder `{ packageName, kind, title, prBody }` is replaced. Second, `packages/engine/src/clients/osv.ts` gains a function that queries many versions of one package in one request (Requirement 2); the existing single-version functions are unchanged. Third, `packages/web/src/load/validate-scan-response.ts` and `packages/web/src/load/lists.ts` accept the new entry shape (Requirement 7). Fourth, the web test generators and the API contract type tests that build `RemediationEntry` values are updated to the new shape. Fifth, a PR that bumps or removes a dependency in `package.json` and leaves `package-lock.json` untouched leaves the two files out of step, so `npm ci` fails on the branch until a human or the Executor runs `npm install`; the PR body states this for bump and for remove (Requirement 5). Sixth, the demo scan generator in `packages/api/scripts` adds a `remediations` list built from recorded fixtures, so the drawer of the demo shows a plan for a Dead package (Requirement 7).

This spec does NOT add the node-sass to sass recipe or any other recipe (R-RM-7), the migration sections of the PR body, branch creation, commits, pull request creation, merging, default-branch resolution, GitHub MCP calls, counting import sites, reading repository source files, editing `package-lock.json`, a persistent Remediation log (DynamoDB belongs to the api), a user-facing control that opens a pull request, changes to the drawer, the CLI, the API handler or the agent. It adds no runtime dependency; `semver` 7.8.6 is already present. The Engine never writes files.

## Glossary

- **Engine**: the @sexton/engine package. Pure core with no AWS, no UI, and no filesystem writes. Network access goes only through the injected Transport.
- **Signal**, **Signal envelope**, **Available signal**, **Unavailable signal**, **Source**, **fetchedAt**, **Cache**, **Packument**, **Full packument**, **Transport**, **ClientContext**: as defined in health-scoring, history-signals and repo-intake.
- **State**: one of Possessed, Dead, Haunted, Restless, Alive, as assigned by the state function.
- **Unhealthy state**: Haunted, Dead or Possessed (R-RM-1). Restless and Alive are not Unhealthy states.
- **Remediation**: a proposed change to the repository that moves a package out of an Unhealthy state (docs/requirements.md section 7).
- **Kind**: one of `bump`, `remove`, `migrate`, the three kinds of Remediation (R-RM-1).
- **RemediationPlan**: the value `planRemediation` returns for one package: `{ packageName, installedVersion, state, stateReason, kind, status, chosenVersion?, majorUpgrade?, reason?, edit? }`. It describes what would be done and carries no I/O.
- **Plan status**: one of `proposed` (a change can be carried out), `no-safe-version` (a bump was attempted and no Passing candidate exists), or `unavailable` (the data or the inputs needed to plan are missing or unusable, with a `reason`).
- **Published version**: a key of the `versions` map of the Full packument that is a valid semver version equal to its own semver-normalised form and at most 64 characters long.
- **Candidate**: a Published version that is greater than the installed version by semver precedence and either has no prerelease part or, WHEN the Declared range is usable and has a comparator with a prerelease part, is In range, kept in Candidate order and cut to the first 20 (Requirement 2). A version equal to or lower than the installed version is never a Candidate, so a downgrade is never proposed.
- **Prerelease comparator**: a comparator of a usable Declared range whose version has a prerelease part, such as `^2.0.0-beta.1`.
- **Candidate order**: in-range Candidates by ascending semver precedence, then out-of-range Candidates by ascending semver precedence. Equal precedence is broken by ascending UTF-16 code-unit order of the version string.
- **In range**: a version that satisfies the Declared range under `semver.satisfies`. WHEN the Declared range is absent or fails `isResolvableRange`, no version is In range.
- **Passing candidate**: a Candidate that is not deprecated and has no advisory of severity Critical, High, Moderate or Unknown. Severity Low passes.
- **Major upgrade**: the label on a bump whose chosen version is not In range. It means "outside the declared range", not a semver major increment.
- **Range style**: the operator form of a usable Declared range: `exact` when the range is a single version (`1.2.3` or `=1.2.3`), `tilde` when it is a single `~` comparator, `caret` when it is a single `^` comparator, and `caret` for every other form, for an absent range and for an unusable one.
- **Styled range**: the new range written into a bump Edit: the chosen version for style `exact`, `~` followed by the chosen version for `tilde`, and `^` followed by the chosen version for `caret`.
- **Bump data**: for one package, the Published versions, the set of deprecated Published versions, and the advisories of each evaluated Candidate, or a failure with a reason.
- **Declared range**: the range string the repository gives a dependency, from `IntakePackage.declaredRange`. Untrusted input.
- **Import sites**: the number of places in the repository's source that import a package. The Executor or the api counts them and passes them to the Engine as a map from package name to a non-negative integer. A missing or unusable entry means unknown.
- **Recipe**: a migration description for one package. Release 0.1 of this spec defines no Recipe.
- **Recipe registry**: a read-only map from package name to Recipe. The default registry, `EMPTY_RECIPE_REGISTRY`, has no entries.
- **Edit**: a structured change to `package.json`: `{ path: "package.json", op, section, name, range? }`, where `op` is `set-range` or `remove-dependency`, `section` is `dependencies` or `devDependencies`, `name` is a Valid package name, and `range` is present only for `set-range`. A `set-range` Edit changes the entry of `name` in `section`. A `remove-dependency` Edit removes `name` from every section of `package.json` that lists it, `dependencies` and `devDependencies` both; its `section` records where intake found the name.
- **PR intent**: the value `buildPrIntent` returns: `{ branch, title, body, files, baseRef }`, where `files` is a list holding one Edit. It is a description. It is not an action.
- **Branch name**: the string `sexton/{kind}-{encoded name}`, built by `branchName` (Requirement 4).
- **Encoded name**: a package name after the escapes of Requirement 4.4.
- **baseRef**: the constant `BASE_REF_DEFAULT`, the string `@default`. It means "the default branch of the repository, resolved by the Executor". It is never a branch name.
- **PR body**: the Markdown text of a pull request description, built by `buildPrBody`.
- **Escaped field**: an upstream or repository string after the escaping rule of Requirement 5.6: control, line-separator and bidirectional characters replaced with a space, backticks replaced, pipes escaped, then truncated to 200 code points (`\|` counts two and is never split), and placed in an inline code span.
- **Executor**: whatever carries out a PR intent: the api handler or the agent, through GitHub MCP. It creates the branch, commits the Edit, opens the pull request, resolves the default branch and records the pull request in the Remediation log.
- **RemediationLogEntry**: `{ repository, branch, prUrl, package, kind, timestamp }` (R-RM-8). `repository` is the Canonical URL of the repository, `prUrl` is an `https://` URL, `package` is a Valid package name, `kind` is a Kind and `timestamp` is an ISO 8601 instant.
- **Remediation log**: an append-only record of RemediationLogEntry values, with no update and no delete.
- **RemediationEntry**: the API response item for one plan: `{ packageName, kind, status, title, summary, prBody, chosenVersion?, majorUpgrade?, intent? }`.
- **Valid package name**, **Untrusted input**, **Canonical URL**, **IntakePackage**, **Declared range**: as defined in repo-intake.
- **Failing rule**: a RuleResult with `pass` false that has at least one Failure whose `name` equals the package name.

## Requirements

### Requirement 1: Plan selection

**User Story:** As a maintainer, I want every dangerous dependency to get exactly one proposed fix, so that I see one clear action per package and none for healthy ones.

#### Acceptance Criteria

1. THE Engine SHALL expose `planRemediation(report, options)`, a pure function that returns a list of RemediationPlan values, where `options` carries the optional `intake` list of IntakePackage values, the optional `importSites` map, the optional `recipes` registry (default `EMPTY_RECIPE_REGISTRY`) and the optional `bumpData` map from package name to Bump data.
2. THE Engine SHALL return exactly one RemediationPlan for each package of the report whose state is Haunted, Dead or Possessed, and none for a package whose state is Restless or Alive, in the order of the report.
3. FOR ANY report, THE Engine SHALL return plans whose `packageName` values are distinct, are names of packages of the report, and belong to packages in an Unhealthy state, and SHALL return a number of plans equal to the number of packages in an Unhealthy state (invariant).
4. THE Engine SHALL choose the Kind in this order and stop at the first match: `migrate` when the Recipe registry has an entry for the package, then `remove` when `importSites` holds exactly 0 for the package, then `bump`.
5. THE Engine SHALL ship `EMPTY_RECIPE_REGISTRY` with no entries, so that `migrate` is never chosen unless the caller injects a registry.
6. WHEN the caller injects a Recipe registry with an entry for an Unhealthy package, THE Engine SHALL choose `migrate` for that package whatever its Import sites, and SHALL give the plan the status `proposed` and no Edit, because the Recipe's edits belong to a later spec.
7. WHEN `importSites` is absent, has no entry for the package, or holds a value that is not a non-negative integer, THE Engine SHALL NOT choose `remove` for that package.
8. FOR ANY report and any `importSites` map, THE Engine SHALL choose `remove` for a package if and only if the package is in an Unhealthy state, has no Recipe, and has an Import sites value of exactly 0 (invariant).
9. THE Engine SHALL give a plan whose chosen Kind is `bump` the status `proposed` when the bump selector returns a Passing candidate, `no-safe-version` when it returns none, and `unavailable` with a `reason` when Bump data is missing, failed, or when the installed version is not a valid semver version.
10. THE Engine SHALL give a plan the status `unavailable`, with a `reason` and no Edit, WHEN the package name is not a Valid package name, WHEN no IntakePackage with the same name is supplied (so the `origin` is unknown) for a Kind that needs an Edit, or WHEN the Branch name exceeds the limit of Requirement 4.6.
11. THE Engine SHALL produce a plan for one package that depends only on that package's own report entry, its own `intake` entry, its own `importSites` value, its own Recipe and its own Bump data, so that adding, removing or reordering other packages leaves the plan unchanged (metamorphic, for any report).
12. FOR ANY report and options, THE Engine SHALL return deeply equal plans from two calls (determinism), and SHALL return a result and SHALL NOT throw, including for a package with all ten signals unavailable or an installed version of `"unresolved"` (rejection).
13. FOR ANY report, THE Engine SHALL leave the report and the options unmodified, and SHALL NOT change the state, the signals or the result of `scorePackages` and `evaluatePolicy` (invariant).
14. THE Engine SHALL plan and describe, and SHALL leave branch creation, commits, pull request creation and merging to the Executor. (review constraint, not a correctness property)

### Requirement 2: Bump candidate selection

**User Story:** As a maintainer, I want the lowest safe version to move to, so that the fix is the smallest change that gets the package out of danger.

#### Acceptance Criteria

1. THE Engine SHALL expose `selectBump(input)`, a pure function with no I/O, whose input holds the installed version, the Declared range (or absent), the Published versions, the set of deprecated Published versions and a map from version to advisories, and which returns either a chosen version with its `majorUpgrade` label or the result `none` with the number of evaluated Candidates.
2. THE Engine SHALL take as Candidates the Published versions that are greater than the installed version by semver precedence and have no prerelease part, and, WHEN the Declared range is usable and has a Prerelease comparator, also the prerelease Published versions that are greater than the installed version and In range, so that a version equal to or lower than the installed version is never proposed and a downgrade is never a bump.
3. FOR ANY input whose Declared range has no Prerelease comparator, THE Engine SHALL exclude every prerelease version from the Candidates and SHALL return a chosen version that has no prerelease part, and FOR ANY input, THE Engine SHALL exclude every version that is not equal to its own semver-normalised form or is longer than 64 characters, and every prerelease version that is not In range (invariant).
4. THE Engine SHALL order the Candidates in Candidate order and SHALL evaluate at most the first 20 of them, so that in-range Candidates are evaluated before out-of-range Candidates, and out-of-range Candidates are evaluated only when fewer than 20 in-range Candidates exist.
5. FOR ANY input, THE Engine SHALL evaluate at most 20 Candidates (boundary, invariant).
6. THE Engine SHALL treat a Candidate as passing if and only if its version is not in the set of deprecated versions and its advisories have no severity of Critical, High, Moderate or Unknown.
7. THE Engine SHALL count severity Unknown as failing, because the advisory could not be graded, so that the selector errs toward not proposing a version it cannot show to be safe.
8. THE Engine SHALL treat a Candidate that has no entry in the advisories map as failing.
9. THE Engine SHALL return the first Passing candidate in Candidate order, which is the lowest Passing candidate among the in-range Candidates when one exists, and otherwise the lowest Passing candidate among the out-of-range Candidates.
10. FOR ANY input, THE Engine SHALL return a chosen version that is a Candidate, is Passing, and has no Passing in-range Candidate below it, and, WHEN the chosen version is out of range, SHALL have no Passing in-range Candidate among the evaluated Candidates (invariant).
11. FOR ANY input, THE Engine SHALL set `majorUpgrade` to true if and only if the chosen version is not In range (invariant).
12. WHEN the Declared range is absent, fails `isResolvableRange` (a git URL, a dist-tag, a `file:` path, an alias, a range longer than 256 characters), or does not parse, THE Engine SHALL treat every Candidate as out of range, so that any chosen version is labelled a Major upgrade. The label then says that the declared range could not be used to confirm compatibility.
13. WHEN no evaluated Candidate passes, or no Candidate exists, THE Engine SHALL return `none`, and the plan SHALL have the Kind `bump`, the status `no-safe-version`, the `reason` `no safe version found among {n} evaluated candidate versions` that states the number of evaluated Candidates, and no Edit and no PR intent.
14. FOR ANY input, THE Engine SHALL return the same result when the list of Published versions is reordered or an entry is repeated (order independence), and the same result when a version that is not greater than the installed version, or a prerelease that is not a Candidate, is added (metamorphic).
15. FOR ANY input, THE Engine SHALL return the same result when an advisory of severity Low is added to a Candidate (metamorphic), and SHALL return `none` or a Candidate that comes later in Candidate order than the chosen version for the same input with an advisory of severity Moderate or above or a deprecation added to the chosen Candidate (monotonic). "Lowest" and "later" in this requirement are positions in Candidate order, not semver comparisons.
16. FOR ANY two calls with deeply equal input, THE Engine SHALL return deeply equal results (determinism), and SHALL return a result and SHALL NOT throw for any strings in the input (rejection).
17. THE Engine SHALL expose `gatherBumpData(ctx, packages)`, which for each package whose planned Kind is `bump` reads the Full packument through `readFullPackument` and the shared `npm-packument` cache key, orders the Candidates with the same function the selector uses, queries OSV for the evaluated Candidates only, and returns a map from package name to Bump data or to a failure with a reason. It SHALL run with a concurrency limit of 8, and SHALL issue no upstream request for a package whose planned Kind is not `bump`, or whose state is Restless or Alive, or whose name is not a Valid package name.
18. THE Engine SHALL send at most one OSV `querybatch` request per package for the initial query, carrying every evaluated Candidate version of that package as one entry of one `queries` array, and SHALL NOT send one request per version.
19. WHEN a `querybatch` response carries a `next_page_token` for some queries, THE Engine SHALL send continuation requests that carry only the queries with a token, and SHALL send at most `OSV_MAX_PAGES` (10) `querybatch` requests per package in total, counting the initial request. WHEN no response carries a token, exactly one `querybatch` request is sent for the package. WHEN a token remains after the tenth request, the advisories of that package are unavailable and the plan says so (Requirement 2.22).
20. THE Engine SHALL fetch `/v1/vulns/{id}` details, because severity is not in the `querybatch` response and the Moderate threshold needs it, at most once per distinct advisory ID per package, through the `osv-vuln` cache key shared with the advisories signal, so that an advisory already read during scoring costs no further request.
21. FOR ANY package and any Transport behaviour, THE Engine SHALL send for the package at most 1 packument request, at most 10 `querybatch` requests and at most as many `/v1/vulns/{id}` requests as the package has distinct advisory IDs across its evaluated Candidates, and none of these for a cached key within 24 hours (invariant, bound).
22. IF the packument read fails, the packument has no `versions` map, the `querybatch` response is malformed, a continuation token remains after the tenth request, or any `/v1/vulns/{id}` fetch fails, THEN THE Engine SHALL return a failure with a reason for that package, SHALL NOT select a version from partial data, and SHALL leave every other package unchanged, so that an upstream failure degrades one plan and never the whole run (N-4).
23. THE Engine SHALL send every request through the Transport with the Sexton User-Agent, SHALL back off with jitter and retry at most three times on HTTP 429 and 503 through `requestWithRetry`, SHALL build the packument URL only from a Valid package name, and SHALL send versions to OSV only as JSON built with `JSON.stringify`. (review constraint, not a correctness property)
24. THE Engine SHALL run no test of this module against the network; every upstream response in tests SHALL be a recorded fixture under `test/fixtures`. (review constraint, not a correctness property)

### Requirement 3: Remove

**User Story:** As a maintainer, I want an unused dependency removed instead of upgraded, so that the risk disappears with the package.

#### Acceptance Criteria

1. WHEN the chosen Kind is `remove` and the package has an `intake` entry, THE Engine SHALL give the plan the status `proposed` and an Edit `{ path: "package.json", op: "remove-dependency", section, name }`, where `section` equals the `origin` of the IntakePackage and `name` equals the package name, and the Edit applies to every section of `package.json` that lists the name, `dependencies` and `devDependencies` both.
2. THE Engine SHALL propose `remove` only on a caller-supplied Import sites value of exactly 0, and SHALL NOT infer Import sites from the report, the signals or any repository text.
3. THE Engine SHALL give a `remove` Edit no `range` field.
4. FOR ANY package in an Unhealthy state with Import sites 0 and no Recipe, THE Engine SHALL return a plan of Kind `remove` whose Edit section equals the package's origin (invariant).
5. FOR ANY package, THE Engine SHALL return the same plan when the Import sites value is replaced by any other value that is not exactly 0 and the Kind falls back to `bump`, except for the fields that depend on the Kind (metamorphic).
6. THE Engine SHALL issue no upstream request for a package whose Kind is `remove`.
7. THE Engine SHALL leave the lockfile, the import statements and every other dependency untouched by the Edit, so that one Edit removes the lines of one package name. (review constraint, not a correctness property)

### Requirement 4: PR intent and branch naming

**User Story:** As a security engineer, I want each proposed fix described as one self-contained intent on a branch of its own, so that an executor can open a reviewable pull request without ever touching the default branch.

#### Acceptance Criteria

1. THE Engine SHALL expose `buildPrIntent(plan, context)`, a pure function that returns a PR intent `{ branch, title, body, files, baseRef }` for a plan whose status is `proposed` and whose Kind is `bump` or `remove`, and returns no intent for any other plan, where `context` carries what the PR body needs (Requirement 5).
2. THE Engine SHALL expose `branchName(kind, name)`, a pure function that returns `sexton/{kind}-{encoded name}` for a Kind and a Valid package name, and returns no branch name for a name that is not a Valid package name or when the result is longer than 200 characters.
3. THE Engine SHALL keep the `@` of a scoped name in the Branch name, so that `@scope/name` yields `sexton/bump-@scope__name`. A leading `@` is valid inside a git ref name, and keeping it separates scoped names from unscoped names. A lone `@` and the sequence `@{` are invalid in a git ref, and neither can occur in a Valid package name.
4. THE Engine SHALL build the Encoded name from the package name by these escapes and no others: `/` becomes `__`; `_` becomes `_u`; `~` becomes `_t`; a `.` becomes `_d` when it is adjacent to another `.`, is the last character, or is the dot of a final `.lock` suffix; every other character is kept. The escapes exist because `/` cannot stay, `~` is forbidden in a git ref, `..`, a trailing `.` and a `.lock` suffix are forbidden in a git ref component, and replacing `/` by `__` alone is not injective (`@a__b/c` and `@a/b__c` are both Valid package names and would collide).
5. FOR ANY Valid package name and any Kind that yields a Branch name, THE Engine SHALL return a Branch name that is a valid git ref name under `git check-ref-format --branch` rules: it contains none of the characters space, `~`, `^`, `:`, `?`, `*`, `[`, backslash, a control character or `{`, contains no `..`, no `//`, no `@{`, does not equal `@`, does not begin or end with `/`, does not end with `.` or `.lock`, and has no component that begins with `.` (invariant).
6. THE Engine SHALL give no Branch name to a package whose Branch name would exceed 200 characters, and the plan SHALL then have the status `unavailable` with the reason "branch name too long".
7. FOR ANY two distinct Valid package names that both yield a Branch name, and any one Kind, THE Engine SHALL return distinct Branch names (injectivity), and FOR ANY Valid package name, decoding the Encoded name by the inverse of Requirement 4.4 SHALL return the original name (round-trip).
8. FOR ANY two different Kinds and any one name, THE Engine SHALL return distinct Branch names, so that the Kind and the name can be recovered by splitting at the first `-` after `sexton/` (injectivity).
9. THE Engine SHALL give every Branch name the prefix `sexton/`, and SHALL build a Branch name only from a Kind of the closed set and a name that passed `isValidPackageName`.
10. THE Engine SHALL set `baseRef` to `BASE_REF_DEFAULT` on every PR intent and SHALL name no other branch to push to than the intent's own `branch`, so that the intent cannot name the default branch, any other existing branch, or a branch outside `sexton/` (invariant, for any plan).
11. FOR ANY report, THE Engine SHALL produce PR intents whose Branch names are pairwise distinct, one intent per plan and one plan per package, so that each pull request carries exactly one remediation and no pull request batches packages (invariant).
12. THE Engine SHALL give a PR intent a `files` list of exactly one Edit with `path` equal to `package.json`, and SHALL carry no file text and no `content` field, so that the Engine never handles repository source text and the Executor applies the Edit to the file it reads. The structured Edit replaces the `{ path, content }` form because it keeps the no-echo guarantee of Requirement 5.
13. THE Engine SHALL give a bump Edit `op` equal to `set-range`, `section` equal to the `origin` of the IntakePackage, and `range` equal to the Styled range of the chosen version in the Range style of the Declared range, so that an exact range stays exact, a tilde range stays tilde, a caret range stays caret and every other form becomes caret, and SHALL leave `package-lock.json` out of `files` (invariant, for any bump plan).
14. FOR ANY bump plan, THE Engine SHALL return an Edit whose `range` satisfies `semver.validRange` and whose lowest matching version is the chosen version (invariant).
15. THE Engine SHALL give the PR intent a `title` of `Sexton: bump {name} to {chosenVersion}` for a bump and `Sexton: remove unused {name}` for a remove, truncated to at most 200 characters, and SHALL build it only from a Valid package name and a Published version.
16. FOR ANY inputs, THE Engine SHALL return deeply equal PR intents from two calls (determinism), and SHALL return a result and SHALL NOT throw (rejection).
17. THE Engine SHALL leave resolving the default branch, creating the branch, applying the Edit, committing and opening the pull request to the Executor, which SHALL NOT push to the default branch and SHALL NOT merge (pr-safety.md). (review constraint, not a correctness property)

### Requirement 5: PR body

**User Story:** As a reviewer with three minutes, I want the pull request to carry its own evidence, so that I can judge the change without leaving the page.

#### Acceptance Criteria

1. THE Engine SHALL expose `buildPrBody(plan, context)`, a pure function that returns a Markdown string, where `context` carries the report entry of the package, the Failing rules that name it, the `generatedAt` of the report and the Engine version, and SHALL build a body for every plan, including a plan with the status `no-safe-version` or `unavailable`, so that the drawer can show the reason.
2. THE Engine SHALL give the PR body, in this order: the title; the package name and installed version; the state and `stateReason`; a Possessed warning line when applicable; a table with one row for every one of the ten signals; the proposed change; the failing policy rules that name the package; a note on the lockfile; and a footer.
3. THE Engine SHALL render in the signals table, for every one of the ten signal names in `SIGNAL_NAMES` order, one row with the signal name, a one-line rendering of its value (or the word "unavailable" and the reason for an Unavailable signal), its `source` and its `fetchedAt`.
4. FOR ANY plan and report entry, THE Engine SHALL include in the PR body the name of each of the ten signals together with the `source` and the `fetchedAt` of that signal, escaped per Requirement 5.6 (invariant).
5. WHEN the plan status is `proposed`, THE Engine SHALL render the proposed change as the Kind, the installed version, the chosen version and the fixed line "Range style preserved" for a bump, with the line "Major upgrade: the chosen version is outside the declared range" when `majorUpgrade` is true, and the removed dependency, the section intake found it in and the fixed text that it is removed from every dependency section that lists it for a remove. THE Engine SHALL NOT print the new range or the old range. WHEN the status is `no-safe-version` or `unavailable`, THE Engine SHALL render "No change proposed" and the plan's `reason`.
6. THE Engine SHALL pass every interpolated string through one escaping function, `escapeField`, which first escapes and then truncates: it replaces every control character, line separator (U+2028, U+2029) and bidirectional control character (U+202A to U+202E, U+2066 to U+2069) with a space, replaces every backtick with an apostrophe, replaces every `|` with `\|`, then truncates the result to at most 200 Unicode code points, counting `\|` as two and never splitting it, with a final "…" when cut, and wraps the result in an inline code span, so that no interpolated string can open an emphasis, a link, an image, a heading, a mention, an HTML tag, an HTML entity, a table cell or a line. The rule applies to every package name, version, signal value, source, reason, advisory summary, maintainer name and rule name, whatever its origin.
7. THE Engine SHALL treat advisory summaries and maintainer names as upstream strings that an attacker can influence, and SHALL render them only through `escapeField`, in at most 20 list items per signal with the text "and N more" for the rest.
8. THE Engine SHALL contain no HTML in the PR body: no tag, no entity written by the Engine, no image and no link other than the text of a `source` inside a code span.
9. THE Engine SHALL NOT render the Declared range, and SHALL NOT render any string taken from the repository other than package names and versions, so that the PR body echoes nothing from the repository. The Declared range is used only to decide the Major upgrade label and appears in the body only as that label's fixed text.
10. FOR ANY plan whose IntakePackage has a Declared range holding an arbitrary string, including Markdown, HTML, a URL or a planted marker, THE Engine SHALL return a PR body that does not contain that string (invariant, no echo).
11. FOR ANY plan, THE Engine SHALL return a PR body in which no line other than a fixed line of the template begins with `#`, `>`, `-`, `*`, a digit followed by `.`, or `|`, unless the Engine wrote it, and no escaped field contains a newline (invariant).
12. THE Engine SHALL include the Possessed warning line, with fixed text that asks the reviewer to check the maintainer, provenance or install-script change before merging, if and only if the state of the package is Possessed (invariant).
13. THE Engine SHALL list in the PR body each Failing rule that names the package, with its index, its type and its name when it has one, and the Failure reason, in at most 20 list items with the text "and N more" for the rest, and SHALL list none when no rule fails for it; FOR ANY policy result, the listed rules SHALL be exactly the first 20 Failing rules whose Failures name the package, in rule order.
14. THE Engine SHALL end every PR body for a plan with the status `proposed` and the Kind `bump` or `remove` with a fixed note that `package-lock.json` is not changed and that `npm install` must be run on the branch before `npm ci` works, and SHALL end the body with a footer that names `ENGINE_VERSION` and the `generatedAt` of the report.
15. FOR ANY plan, THE Engine SHALL return a PR body of at most 60000 UTF-16 code units, below the 65536-character limit of GitHub, by the per-list limit of 20 items and the 200-code-point field limit, and SHALL render again with a per-list limit of 5 when the first render is longer (boundary, invariant).
16. FOR ANY inputs, THE Engine SHALL return deeply equal PR bodies from two calls (determinism), and SHALL read no clock, so that the only time in the body is `generatedAt` and the `fetchedAt` values.
17. FOR ANY string, `escapeField` SHALL return a string of at most 203 Unicode code points that contains no newline, no backtick other than the two delimiters, and no unescaped `|` (invariant), and SHALL return the same result from two calls (determinism).

### Requirement 6: Remediation log

**User Story:** As a security engineer, I want a record of every pull request Sexton opened that cannot be edited afterwards, so that I can hand an auditor the remediation log as evidence.

#### Acceptance Criteria

1. THE Engine SHALL define `RemediationLogEntry` as `{ repository, branch, prUrl, package, kind, timestamp }`, where `repository` is a Canonical URL, `branch` begins with `sexton/`, `prUrl` begins with `https://`, `package` is a Valid package name, `kind` is a Kind and `timestamp` is an ISO 8601 instant that parses.
2. THE Engine SHALL define the `RemediationLog` interface with exactly two methods, `append(entry)` and `list()`, both returning promises, so that the api can implement it over DynamoDB. The interface SHALL have no method that updates, replaces, deletes or clears an entry.
3. THE Engine SHALL expose `createInMemoryRemediationLog()`, which returns a RemediationLog that keeps entries in insertion order.
4. WHEN `append` receives an entry that satisfies Requirement 6.1, THE Engine SHALL add a copy of the entry at the end and resolve with `{ ok: true }`; WHEN it receives anything else, THE Engine SHALL change nothing and resolve with `{ ok: false, reason }`, where `reason` is a fixed text that contains no part of the entry (rejection, for any value).
5. FOR ANY sequence of valid entries appended to a new log, `list()` SHALL return the entries in the order appended, with no entry missing and none added (append-only).
6. FOR ANY log and any valid entry, the list after `append` SHALL equal the list before `append` followed by the entry, so that every earlier entry is unchanged and in the same position (monotonic, append-only).
7. FOR ANY log, THE Engine SHALL return from `list()` a copy that is frozen, so that changing the returned list, or changing an entry object after it was appended, leaves the log unchanged (invariant).
8. FOR ANY entry rejected by `append`, `list()` SHALL return a list equal to the list before the call (invariant).
9. THE Engine SHALL leave recording every pull request in the log before returning to the caller to the Executor, and SHALL leave persistence to the api. (review constraint, not a correctness property)

### Requirement 7: Contract and attachment

**User Story:** As a maintainer using the cemetery, I want the remediation for each package delivered with the scan, so that the drawer shows what Sexton would do and why.

#### Acceptance Criteria

1. THE Engine SHALL define `RemediationEntry` as `{ packageName, kind, status, title, summary, prBody, chosenVersion?, majorUpgrade?, intent? }`, where `status` is a Plan status, `summary` is one line of at most 200 characters, and `intent` is a PR intent, and `packages/api/src/contract.ts` SHALL re-export it, replacing the placeholder, so that `ScanResponse.remediations` is a list of the new type.
2. THE Engine SHALL expose `attachRemediations(report, policyResult, plans)`, a pure function that returns a list of RemediationEntry values, one per plan, in plan order, without mutating its arguments.
3. FOR ANY report, policy result and plans, THE Engine SHALL return entries whose `packageName` values are distinct and equal the `packageName` of the plans, whose `kind` and `status` equal those of the plan, and whose `prBody` equals `buildPrBody` for the plan (invariant).
4. THE Engine SHALL give an entry a `title` equal to the PR intent title when an intent exists, and the title `Sexton: no change proposed for {name}` otherwise.
5. THE Engine SHALL set `chosenVersion` and `majorUpgrade` on an entry if and only if the plan has them, and `intent` if and only if `buildPrIntent` returns one (invariant).
6. THE Engine SHALL build the Failing rules of each package from the policy result alone, so that a package with no Failing rule gets an empty list.
7. WHEN a plan names a package that is absent from the report, THE Engine SHALL skip that plan and SHALL NOT throw.
8. FOR ANY report, policy result and plans, THE Engine SHALL return entries that survive `JSON.parse(JSON.stringify(entries))` unchanged (round-trip) and that contain no `undefined` value.
9. THE Engine SHALL leave `scorePackages` unchanged, so that for any packages it returns the report it returned before this spec (invariant), and SHALL add no field to the report.
10. THE web validator `validateScanResponse` SHALL accept a `remediations` list whose entries have string `packageName`, `title`, `summary` and `prBody`, a `kind` in `REMEDIATION_KINDS`, a `status` in the new `REMEDIATION_STATUSES`, an optional string `chosenVersion`, an optional boolean `majorUpgrade`, and an optional `intent` that is an object with string `branch`, `title`, `body` and `baseRef` and an array `files`. A repeated `packageName` SHALL still give `DUPLICATE`, an absent `remediations` field SHALL still be accepted, and an entry in the old placeholder shape (no `status`, no `summary`) SHALL be rejected with `MISSING_FIELD`, so that valid responses are not rejected and the old shape is not silently accepted.
11. FOR ANY valid response built from the new shape, `validateScanResponse` SHALL return `{ ok: true }` with a value deeply equal to the input (round-trip), and FOR ANY single fault in a remediation entry (a removed required field, a wrong type, a `kind` or `status` outside its set), SHALL return `{ ok: false }` with an error whose path is the faulty location and which contains no string from the input.
12. THE web drawer SHALL keep showing the kind, the title and the `prBody` of the entry for the selected package, read as text, and SHALL need no code change; the web list `REMEDIATION_STATUSES` SHALL be kept equal to the Engine list by the same compile-time check that guards the other literal lists. The web change is limited to the validator, `lists.ts`, and the tests that build entries. (review constraint, not a correctness property)
13. THE demo scan generator SHALL add a `remediations` list built by `planRemediation` and `attachRemediations` from the recorded remediation fixtures, offline, so that the demo drawer shows a remediation title and PR body for a Dead package, and the generated demo scan SHALL pass `validateScanResponse`.

### Requirement 8: Untrusted input

**User Story:** As a security engineer, I want everything read from a repository or an upstream treated as hostile data, so that a crafted package cannot steer a branch name, a request or the text of a pull request.

#### Acceptance Criteria

1. THE Engine SHALL treat package names, installed versions, Declared ranges, Import sites values, packument contents and OSV contents as Untrusted input, and SHALL use no `eval`, no `Function` constructor, no dynamic `import` or `require`, no shell command and no template rendering on it. (review constraint, not a correctness property)
2. THE Engine SHALL call `isValidPackageName` on a name before the name is used in a Branch name, a URL, a cache key, an Edit or a PR body, and SHALL give a plan for a name that fails the check the status `unavailable`, no Edit, no intent and no upstream request.
3. FOR ANY name, THE Engine SHALL return a Branch name only for a name that passes `isValidPackageName` (invariant).
4. THE Engine SHALL use a version in an Edit, a title, a cache key or a request only when it is a Published version, that is, valid semver, equal to its own normalised form and at most 64 characters, and SHALL use the installed version in a request or a cache key only when it equals its own normalised form.
5. THE Engine SHALL use a Declared range only as the argument of `isResolvableRange` and `semver.satisfies`, and SHALL NOT use it in a URL, a cache key, a Branch name, an Edit, a title or a PR body.
6. THE Engine SHALL read every packument and OSV field by own-property access, SHALL read `versions`, `deprecated` and `vulns` only from objects whose types it has checked, and SHALL handle a name such as `constructor`, `prototype` or `toString` as an ordinary key, so that `Object.prototype` is never read or changed.
7. THE Engine SHALL treat a malformed packument or OSV response, including one with wrong types, huge arrays, or version strings that are not strings, as a failure of Bump data for that package, and SHALL NOT throw for any JSON value.
8. FOR ANY package.json-derived or upstream string that contains Markdown, HTML, a newline, a backtick, a pipe or a planted marker, THE Engine SHALL return a PR intent and a PR body in which the planted string appears only inside an Escaped field, or not at all, and SHALL return a Branch name that contains none of its characters outside the allowed set (invariant).
9. THE Engine SHALL send no Authorization header, no Cookie header and no token on any request, and SHALL log no packument, advisory or response body. (review constraint, not a correctness property)
10. THE Engine SHALL retain only package names, versions, severities, advisory IDs and capped text in a plan, an intent, a body or an entry, and SHALL store no source code, so that N-2 holds.
