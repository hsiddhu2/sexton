# Bugfix Requirements Document
## Introduction
The hosted site at https://de1giv8lj8sfh.cloudfront.net serves every web file with no `Cache-Control` header. The CloudFront distribution adds none, and the bucket deployment writes none to the S3 objects. A browser then picks its own freshness lifetime for each file. Under the HTTP caching rules that is a heuristic lifetime, typically a tenth of the time since the file's `Last-Modified` date, and during that time the browser does not ask the server at all.
Evidence, found after deploy 4 on 26 Nov 2026 UTC and reproduced twice in a browser that had opened the site before the deploy:
- `/` came from the browser cache (`transferSize` 0) and loaded the old bundle `index-tDpRQ5lZ.js`, although CloudFront already served the new `index.html` with `index-rdKLS1Oq.js` (`x-cache: Miss from cloudfront`, `last-modified` 02:24 UTC).
- With a query string added to bypass the cached page, the new application loaded, but the browser still held the old `demo/scan.json`. The page showed "Scan could not be loaded" with `MISSING_FIELD` for `/report/packages/0/signals/newDependency` and `/report/packages/0/signals/publisherChange`. A fetch of `demo/scan.json` from the page returned the old body; the same fetch with `cache: "reload"` returned the new one.
- A hard reload fixed both. Judges and returning visitors will not know to do that.
The bug condition is: a browser holds a copy of a web file whose name carries no content hash (`index.html`, the files under `demo/`, `replay/` and `fonts/`), the copy is older than the file on the site, and the copy is still inside its heuristic lifetime. The browser then uses the old copy without asking.
The fix adds the header at CloudFront with two response headers policies. Every web file outside `assets/` gets `Cache-Control: no-cache`, so the browser revalidates it on every use. Files under `assets/`, whose names carry a content hash, get `Cache-Control: public, max-age=31536000, immutable`. The API behaviours keep their current policy. As a second guard, the web loader fetches a static `.json` scan once more, bypassing the browser cache, when the first copy fails the format check.
Limit: a browser that stored a file before deploy 5 stored it without the header, so it may use that copy until the copy's heuristic lifetime ends. The fix protects every copy fetched after deploy 5. The loader guard also covers the old-demo-data case for any browser that runs the fixed bundle.
## Bug Analysis
### Current Behavior (Defect)
1.1 WHEN CloudFront answers a request for `index.html`, the site root, a path that falls back to `index.html`, or any file under `demo/`, `replay/`, `fonts/` or `assets/` THEN the system sends no `Cache-Control` header, so the browser chooses a heuristic freshness lifetime
1.2 WHEN a browser that loaded the site before a deploy opens it again after the deploy, inside the heuristic lifetime of its copy of `index.html` THEN the system shows the old application from the browser cache with no request to the site
1.3 WHEN a browser runs the new application but still holds a copy of `demo/scan.json` from before the deploy THEN the system shows "Scan could not be loaded" with `MISSING_FIELD` errors for fields the new format requires
1.4 WHEN the web loader receives a static scan file that fails the format check THEN the system shows the error at once, without asking the site whether a newer copy exists
### Expected Behavior (Correct)
2.1 WHEN CloudFront answers a request on the default behaviour, which covers `index.html`, the site root, every path that falls back to `index.html`, and every file under `demo/`, `replay/` and `fonts/` THEN the system SHALL send `Cache-Control: no-cache`, replacing any `Cache-Control` from the origin
2.2 WHEN CloudFront answers a request whose path starts with `/assets/` THEN the system SHALL send `Cache-Control: public, max-age=31536000, immutable`, replacing any `Cache-Control` from the origin
2.3 WHEN a browser that fetched the site after deploy 5 opens it again after a later deploy THEN the system SHALL serve the new `index.html` and the new files under `demo/` and `replay/` on a normal load or reload, because the browser revalidates each of them, with no hard reload
2.4 WHEN the web loader loads an address whose path ends in `.json` and the response fails the format check (`invalid-response`) THEN the system SHALL fetch the same address once more with `cache: "reload"` and the same other fetch options, and SHALL use the result of that second fetch, whatever it is
2.5 WHEN the web loader loads an address whose path does not end in `.json`, such as `/api/scan`, or the first response is anything other than `invalid-response` THEN the system SHALL NOT fetch a second time
2.6 WHEN the web build writes a file under `assets/` THEN the file name SHALL carry a content hash, because the web package's public folder has no `assets` folder and the build configuration does not override the bundler's default output names or folder
2.7 WHEN the owner runs the cache header check against the hosted site THEN the system SHALL print the `Cache-Control` header of `index.html`, `demo/scan.json`, `replay/axios.json`, one hashed file under `assets/` named in `index.html`, each with PASS or FAIL against the expected value, and one path that falls back to `index.html` marked INFO, and SHALL exit with a non-zero status if any PASS or FAIL line is FAIL. The INFO line does not count towards the exit status
2.8 WHEN a reader opens `build/infra/10-deploy.md` or `docs/architecture.md` THEN the system SHALL describe the two new response headers policies and the cache header check, and the runbook SHALL list the check as a smoke check
### Unchanged Behavior (Regression Prevention)
3.1 WHEN CloudFront answers a request on `/api/remediate` or `/api/*` THEN the system SHALL CONTINUE TO use the existing `SecurityHeaders` policy with no custom header, and caching SHALL CONTINUE TO be disabled for those paths
3.2 WHEN CloudFront answers any request on any behaviour THEN the system SHALL CONTINUE TO send the same content security policy, HSTS of two years with subdomains, `nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`, each overriding the origin
3.3 WHEN CloudFront caches web files THEN the system SHALL CONTINUE TO use the managed CachingOptimized policy and the same S3 origin with origin access control, and the bucket deployment SHALL CONTINUE TO invalidate `/*` after it copies the web build
3.4 WHEN a viewer requests a path the bucket does not hold THEN the system SHALL CONTINUE TO answer with `/index.html` and status 200, with an error caching time of 0
3.5 WHEN the stacks are synthesised THEN the system SHALL CONTINUE TO leave the Data stack, the `GithubTokenSecret` resource, every IAM role and policy, the bucket policy and the number of origin access controls unchanged, and `cdk synth --strict` and cdk-nag AwsSolutions SHALL CONTINUE TO pass with no new acknowledgement
3.6 WHEN the web loader gets a valid response, a fetch failure, a non-2xx status, a body over the size limit or a body that is not JSON THEN the system SHALL CONTINUE TO give the same result as before with one fetch, SHALL CONTINUE TO never reject, and every fetch, the second one included, SHALL CONTINUE TO use `credentials: "omit"`, `redirect: "error"`, `referrerPolicy: "no-referrer"`, the `Accept: application/json` header, the abort signal and the size limit
